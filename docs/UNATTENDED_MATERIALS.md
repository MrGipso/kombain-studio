# Автономное производство материалов

Основной production-сценарий:

1. Пользователь утверждает сцены.
2. Пользователь утверждает кадры.
3. Preflight проверяет freshness, покрытие транскрипта, соответствие кадров
   карточкам, Context Bible, continuity-группы, важные визуальные якоря и
   слишком долгие повторы концепта.
4. Кнопка **Создать все материалы** запускает серверную задачу. Работа не
   принадлежит вкладке браузера и сохраняет checkpoint после каждой операции.

Перед запуском движок атомарно записывает `.material_plan.json`. В плане явно
связаны `segment_ids → visual_concept_id → asset_request_id → edit_span`, а
также зафиксирован полный граф provider-операций. Весь snapshot защищён
контрольной суммой и не принимается после ручного повреждения.
Исполнение хранится отдельно в `.material_run.json`, поэтому результаты и
творческий план не смешиваются. Checkpoint имеет собственную контрольную сумму
и предыдущую атомарную копию `.material_run.backup.json`; при повреждении
основного файла движок продолжает с последнего целого состояния.

Политика по умолчанию:

- уже готовые файлы не перезаписываются;
- генерация сгруппирована по фазам, чтобы не менять модели в VRAM на каждом
  кадре;
- LTX-видео сразу создаётся полным workflow: автономный запуск не оставляет
  черновики, требующие последующей кнопки «Финал»;
- изображение и видео получают не более двух попыток;
- использованные попытки сохраняются в checkpoint и не обнуляются после
  аварийного перезапуска;
- переходы `queued → running → interrupted/succeeded/failed/cancelled`
  проверяются state machine и записываются в краткую историю;
- путь к частично записанному или нечитаемому файлу не считается завершённой
  операцией: материал повторно создаётся в пределах оставшегося retry-бюджета;
- после исчерпания попыток создаётся Ken Burns из доступного изображения;
- если недоступен и FFmpeg, слот остаётся заполненным безопасным статичным
  изображением;
- subjective vision-QA не запускается;
- проверяются только объективные свойства файла: он существует, читается и
  имеет положительную длительность;
- если ComfyUI временно пропал во время очереди, задача сохраняет checkpoint,
  ждёт восстановления сервиса и не превращает все оставшиеся кадры в fallback;
- перед стартом только реально нужные Krea/Ideogram/LTX workflow сверяются с
  живым списком нод ComfyUI;
- continuity-группы имеют явный граф `anchor image → dependent images`; один
  проектный canonical reference проверяется по SHA-256 и не заменяется цепочкой
  предыдущих кадров;
- повторяющаяся системная ошибка провайдера (например CUDA OOM) останавливает
  очередь после исчерпания попыток и не создаёт fallback для всего проекта;
- незавершённый checkpoint автоматически подхватывается после перезапуска,
  когда ComfyUI снова доступен.
- отмена серверной очереди удаляет ожидающий prompt из ComfyUI; глобальный
  interrupt вызывается только когда живое состояние очереди подтверждает, что
  выполняется именно prompt этого проекта;
- frozen material plan версии 3 сохраняет скомпилированные provider-prompts,
  reference-граф и отпечаток reference-workflow; планы версий 1–2 остаются
  читаемыми для восстановления незавершённых запусков.

## Watchdog ComfyUI

Встроенный watchdog запускается вместе с сервером Комбайна, но включается
отдельной настройкой. Он проверяет `/system_stats`, игнорирует единичные сетевые
сбои и начинает восстановление только после заданного числа неудач подряд.
Перезапускается исключительно portable-установка из `comfy_install_dir`:
исполняемый файл и `ComfyUI/main.py` проверяются заранее, процесс запускается
напрямую без shell, а завершать watchdog имеет право только процессы с точно
совпадающим Python и командной строкой ComfyUI.

После успешного восстановления API движок подхватывает незавершённые material
checkpoints. Частота перезапусков ограничена скользящим окном; после исчерпания
лимита статус становится `restart_limit`, и требуется устранить первопричину.
Текущий статус доступен по `GET /api/system/comfy-watchdog` и отображается рядом
с кнопкой автономного производства.

Для локального интерфейса достаточно `127.0.0.1`. Чтобы обращаться к ComfyUI и
локально, и через ZeroTier, укажите `0.0.0.0`; ограничение доступа в этом случае
должно обеспечиваться Windows Firewall. ComfyUI принимает один адрес
`--listen`, а не список через запятую.

Preflight блокирует разрывы/наложения таймлайна, несовпадение Scene → Shot →
Asset Card, потерянные сегменты, изменение текста сцены относительно
транскрипта, нестабильные идентификаторы и противоречия контекста внутри
непрерывного действия. Имена и числа назначаются конкретному кадру по
максимальному пересечению с сегментом речи.

Контекстная модель и границы reference-consistency описаны в
[`CONTEXT_STORYBOARD.md`](CONTEXT_STORYBOARD.md).

Preflight-блокеры останавливают запуск до исправления плана. Предупреждения не
останавливают производство: смысловые решения нельзя надёжно исправлять
автоматически без риска изменить авторский замысел.

## API

- `GET /api/projects/{project_id}/materials/preflight`
- `GET /api/projects/{project_id}/materials/run`
- `POST /api/projects/{project_id}/materials/run`

POST возвращает `202` после создания durable job. Прогресс доступен и через
material-run checkpoint, и через общий SQLite-реестр задач проекта.

## Честные границы

Checkpoint защищает от перезагрузки страницы и позволяет продолжить после
перезапуска приложения. Watchdog может восстановить завершившийся или зависший
процесс ComfyUI, но не чинит CUDA OOM, несовместимые custom nodes, ошибочный
workflow, драйвер GPU или выключенный компьютер. Гарантированный fallback также не
может победить заполненный диск, повреждённую файловую систему или полный отказ
записи; такие случаи остаются явной ошибкой задачи.
